Вчерашнее «O(1) в среднем» молча предполагало, что *данные* равномерно размазываются по вёдрам, — и атака ×146 показала цену этого предположения. Сегодня усредняем по-другому: случайной делаем **саму функцию**. Противник знает алгоритм, но не знает случайного семени — и не может подобрать плохой вход. Это тот же переход, что у quicksort со случайным пивотом (семестр 1, занятие 21). Замеры реальные (Apple M-серия, `clang++ -O2`).

## Универсальное хеширование

> [!def] Универсальное семейство
> Набор функций $H$ (каждая из $U$ в $\{0, \dots, m-1\}$) **универсален**, если для любых двух различных ключей $x \ne y$:
> $$P_{h \in H}\left[ h(x) = h(y) \right] \le \frac{1}{m}.$$
> Вероятность — по случайному выбору $h$ из $H$; ключи любые, хоть подобранные противником.

Функция выбирается один раз при создании таблицы (случайным семенем), дальше детерминирована — как и положено хешу. «Идеальная случайная функция» тоже подошла бы, но её негде хранить: таблица значений размером со вселенную ключей. Нужно семейство с коротким описанием.

> [!theorem] Ожидаемая длина цепочки
> Для любого набора из $n$ ключей и любого ключа $x$ из него ожидаемая длина цепочки ведра $h(x)$ не превышает $1 + \frac{n-1}{m} < 1 + \alpha$.
> {{% notice style="prove" expanded="true" %}}
Длина цепочки — это $1$ плюс число ключей $y \ne x$, столкнувшихся с $x$. Матожидание суммы индикаторов равно сумме вероятностей (линейность):
$$E[\text{len}] = 1 + \sum_{y \ne x} P[h(x) = h(y)] \le 1 + \frac{n-1}{m}.$$
Каждое слагаемое не превышает $1/m$ по определению универсальности. Приём «индикаторы + линейность» — уже третий раз в курсе: так считали глубину случайного BST (лемма о предке, занятие 2) и сравнения quicksort.
{{% /notice %}}

Существенно: гарантия «в среднем по $h$» верна для **любого** набора данных — в отличие от «в среднем по данным», которая для злых данных не значила ничего.

### Конструкция Картера–Вегмана

$$h_{a,b}(k) = ((a \cdot k + b) \bmod p) \bmod m,$$

где $p$ — простое, большее любого ключа; $a \in [1, p)$, $b \in [0, p)$ — случайное семя. Хранить нужно два числа, стоимость — умножение и два остатка.

```cpp
struct UniHash {
    static constexpr uint64_t p = 4'294'967'311ull;   // простое > 2^32
    uint64_t a, b;                                    // случайное семя
    UniHash() {
        std::mt19937_64 r(std::random_device{}());
        a = r() % (p - 1) + 1;
        b = r() % p;
    }
    size_t operator()(int k) const { return size_t((a * uint64_t(uint32_t(k)) + b) % p); }
};
std::unordered_set<int, UniHash> safe;                // подключение — один параметр шаблона
```

Тонкость для педантов: при $a > 2^{32}$ произведение `a * k` может переполнить uint64, и «mod $2^{64}$» вмешается раньше `% p` — формула нарушается с вероятностью около $3 \cdot 10^{-9}$. Строгая версия перемножает в `unsigned __int128`; для практики и замеров достаточно кода выше.

{{% expand title="Доказательство универсальности семейства Картера–Вегмана" %}}
Фиксируем $x \ne y$ (оба меньше $p$). Обозначим $r = (a x + b) \bmod p$, $s = (a y + b) \bmod p$.

**Шаг 1: $r \ne s$.** Иначе $a(x - y) \equiv 0 \pmod p$, а $p$ простое и оба сомножителя ненулевые по модулю $p$ — противоречие.

**Шаг 2: пары $(r, s)$ равновероятны.** Система «$ax + b \equiv r$, $ay + b \equiv s$» имеет ровно одно решение $(a, b)$ для каждой пары $r \ne s$ (вычитаем: $a \equiv (r-s)(x-y)^{-1}$, обратный существует, так как $p$ простое; затем $b$ восстанавливается). Значит, выбор случайных $(a, b)$ равносилен выбору случайной пары $r \ne s$.

**Шаг 3: считаем коллизии.** $h(x) = h(y)$ означает $r \equiv s \pmod m$. При фиксированном $r$ подходящих $s \ne r$ — не больше $\lceil p/m \rceil - 1 \le (p-1)/m$ из $p - 1$ возможных. Итого $P[\text{коллизия}] \le 1/m$. ∎
{{% /expand %}}

### Проверка боем

```
# те же 20 000 ключей, кратных bucket_count = 100 003
std::hash (тождественный):    263 мс    все ключи — в 1 ведре
UniHash (a, b случайные):     0.5 мс    вёдер занято: 20 000
```

«Злым» был не набор ключей, а его резонанс с *известной* функцией: смените функцию на неизвестную — резонанс исчез. В продакшене так и сделано: Python и Rust хешируют строки SipHash-ом со случайным семенем (у Python — общим на процесс, у Rust — своим на каждую таблицу); Java 8 пошла другим путём — длинное ведро HashMap превращается в красно-чёрное дерево (занятие 2), давая худший случай $O(\log n)$. А вот `std::hash` в C++ семени не имеет до сих пор — поэтому вчерашняя атака и удалась.

## Совершенное хеширование

Если набор из $n$ ключей **фиксирован** (ключевые слова языка, коды стран, словарь), можно потребовать большего: ноль коллизий, $O(1)$ в *худшем* случае, $O(n)$ памяти. Это даёт двухуровневая схема **FKS** (Фредман–Комлош–Семереди):

- **уровень 1** — универсальный хеш в $m = n$ вёдер; коллизии допускаются;
- **уровень 2** — ведру с $n_i$ ключами выделяется вторичная таблица размера $n_i^2$ со своим хешем $h_i$, который **подбирается** (перевыбором семени), пока коллизий не станет ноль.

Поиск: два хеша, два прыжка — константа без всяких «в среднем».

**Почему подбор быстрый.** В таблице размера $n_i^2$ ожидаемое число коллизий $\le \frac{n_i(n_i-1)}{2} \cdot \frac{1}{n_i^2} < \frac{1}{2}$ — по неравенству Маркова бесколлизионный хеш находится с вероятностью больше половины: в среднем хватает двух попыток. Парадокс дней рождения, обращённый в союзника: $n^2$ вёдер на $n$ ключей — простор.

**Почему память линейная.** $\sum_i n_i^2 = n + 2\sum_i \binom{n_i}{2}$, а сумма $\binom{n_i}{2}$ — это в точности число коллизий верхнего уровня, ожидание которого при универсальном хеше не превышает $\binom{n}{2}/m = (n-1)/2$. Итого $E\left[\sum_i n_i^2\right] < 2n$: суммарный второй этаж — линейный.

Где встречается: **gperf** (совершенные хеши для ключевых слов GCC/Clang), парсеры протоколов с constexpr-таблицами в .rodata, минимальные совершенные хеши (CHD, BBHash) для гигантских неизменяемых словарей — поисковые индексы, биоинформатика (~2–3 бита на ключ). Общий знаменатель: **build once — read many**.

## Сортировка Киркпатрика–Рейша

Сравнениями быстрее $\Omega(n \log n)$ нельзя (семестр 1, занятие 23), но целые ключи — не чёрные ящики. Radix идёт фиксированными порциями по $r$ бит — $w/r$ проходов. Киркпатрик и Рейш (1984) предложили **рекурсию**: разрезать ключ пополам на старшую и младшую половины и свести сортировку $w$-битных ключей к сортировкам $(w/2)$-битных:

1. сгруппировать ключи по старшей половине — **хеш-таблицей** ($O(n)$ времени и памяти; прямая адресация потребовала бы массив на $2^{w/2}$ ячеек);
2. рекурсивно отсортировать множество старших половин (в рекурсию уходит по одному представителю группы — тонкость, удерживающая суммарный размер);
3. рекурсивно отсортировать младшие половины внутри каждой группы;
4. база: ключи короче $\log_2 n$ бит сортируются прямой адресацией за $O(n)$.

Биты половинятся, пока не станут короче $\log n$: глубина рекурсии $\log_2(w/\log_2 n)$, каждый уровень линеен — итого $O(n \log(w/\log n))$. При $w = 64$ и $n = 10^6$ это буквально пара уровней. Без хеширования конструкция не работает вовсе — вот зачем сортировке хеш-таблица.

Честная оговорка: полный KR — теоретический рекорд и олимпиадная экзотика (хеш-группировки на каждом уровне несут большие константы). Но его нулевой этаж — «сортируй по структуре ключа» — работает и в быту:

```
# сортировка 10^7 случайных uint64
std::sort:          183 мс
radix 4 × 16 бит:    82 мс     # ×2.2
```

## Задачи семинара

1. **Семейство всех функций.** Докажите, что множество всех функций из $U$ в $\{0..m-1\}$ — универсальное семейство. Почему им нельзя пользоваться?

   {{% expand title="Разбор" %}}Для случайной функции значения $h(x)$ и $h(y)$ независимы и равномерны, поэтому $P[h(x)=h(y)] = 1/m$ — универсальность выполнена с равенством. Но выбранную функцию надо *хранить*: таблица её значений — $|U| \cdot \log_2 m$ бит (для 32-битных ключей и $m = 2^{16}$ — восемь гигабайт). Картер–Вегман сжимает «случайность» до двух чисел — в этом и есть содержание конструкции: универсальность почти бесплатно.{{% /expand %}}

2. **FKS руками.** Ключи $\{27, 40, 52, 60, 71, 3, 12, 75, 84\}$, верхний хеш $h(k) = k \bmod 9$. Разложите по вёдрам, выпишите размеры вторичных таблиц и суммарную память.

   {{% expand title="Разбор" %}}Остатки mod 9: 27→0; 3, 12, 75, 84→3; 40→4; 60→6; 52→7; 71→8. Вёдра: $n_0=1$, $n_3=4$, $n_4=1$, $n_6=1$, $n_7=1$, $n_8=1$ (вёдра 1, 2, 5 пусты). Вторичные таблицы: $1 + 16 + 1 + 1 + 1 + 1 = 21$ ячейка при $n = 9$ — это $2.3n$: чуть выше ожидания $2n$, что нормально для одного конкретного расклада (оценка была в среднем). Одно «жирное» ведро съело почти всю память — и всё равно осталось линейно.{{% /expand %}}

3. **Совершенство и динамика.** Почему одна вставка ломает совершенный хеш и как с этим жить?

   {{% expand title="Разбор" %}}Новый ключ может столкнуться с существующим во вторичной таблице — «совершенство» по построению относится к фиксированному набору. Жить можно амортизацией (занятие 10 семестра 1): копить вставки в маленькой обычной таблице и раз в $\Theta(n)$ операций перестраивать FKS целиком — ожидаемое $O(n)$ на перестройку размазывается в $O(1)$ на операцию. Альтернатива — **cuckoo-хеширование**: у каждого ключа два допустимых «дома» ($h_1(k)$ и $h_2(k)$), вставка выселяет постояльца в его второй дом по цепочке; поиск — максимум два прыжка в худшем случае, динамика разрешена. Про него стоит почитать любознательным.{{% /expand %}}
