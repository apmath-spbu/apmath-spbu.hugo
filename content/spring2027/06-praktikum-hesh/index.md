Практикум блока хеширования: теория закрыта занятиями 4–5, сегодня — инженерия. Пишем обе таблицы руками, меряем цену рехеширований, наступаем на главные грабли открытой адресации (могилки и дубликаты), учим строки и свои структуры быть ключами. Судья прежний — `std::unordered_set` и стресс-тест; замеры реальные (Apple M-серия, `clang++ -O2`).

## Цепочки: ChainSet

Учебник рисует в ведре связный список — мы берём `vector`: элементы ведра лежат подряд и проход по коллизиям дружит с кэшем (семестр 1, занятие 8).

```cpp
struct ChainSet {
    std::vector<std::vector<int>> b;      // вёдра
    size_t n = 0;                         // ключей всего
    double maxLoad = 1.0;                 // порог α

    explicit ChainSet(size_t m = 8) : b(m) {}
    size_t bucket(int k) const { return size_t(uint32_t(k)) % b.size(); }

    bool find(int k) const {
        for (int x : b[bucket(k)]) if (x == k) return true;
        return false;
    }
    void insert(int k) {
        auto& v = b[bucket(k)];
        for (int x : v) if (x == k) return;         // дубликат
        v.push_back(k); ++n;
        if (double(n) / b.size() > maxLoad) rehash(2 * b.size());
    }
    void erase(int k) {
        auto& v = b[bucket(k)];
        for (auto& x : v)
            if (x == k) { x = v.back(); v.pop_back(); --n; return; }
    }
    void rehash(size_t m2) {
        std::vector<std::vector<int>> nb(m2);
        for (auto& v : b)
            for (int x : v) nb[size_t(uint32_t(x)) % m2].push_back(x);
        b = std::move(nb);                          // зан. 22
    }
    void reserve(size_t cap) { if (cap > b.size()) rehash(cap); }
};
```

Детали, которые кусаются: приведение `uint32_t(k)` до взятия остатка — отрицательный ключ со знаковым `%` дал бы отрицательное ведро (семестр 1, занятие 3); инвариант «ключ живёт только в ведре bucket(k)» — рехеш единственное место, где ключи переезжают; erase свопом с последним — цепочка не обязана хранить порядок.

**Рехеширование** — та же экономика ×2, что у vector (амортизация — семестр 1, занятия 10 и 16). Ведро ключа при смене m меняется, поэтому только полная перекладка:

```
# вставка 10^6 ключей в ChainSet
без reserve:   118 мс     # рехеши по дороге
с reserve:      71 мс     # ×1.7
```

## Открытая адресация: OpenSet

Один массив, три состояния ячейки: EMPTY, FULL и — после первого же удаления — DEAD.

```cpp
struct OpenSet {
    enum State : uint8_t { EMPTY, FULL, DEAD };
    std::vector<int>   key;
    std::vector<State> st;
    size_t n = 0;
    explicit OpenSet(size_t m) : key(m), st(m, EMPTY) {}

    bool find(int k) const {
        size_t m = key.size(), i = size_t(uint32_t(k)) % m;
        while (st[i] != EMPTY) {                    // сквозь могилки
            if (st[i] == FULL && key[i] == k) return true;
            i = (i + 1) % m;                        // линейная проба
        }
        return false;                               // пустота = стоп
    }
    void insert(int k) {
        size_t m = key.size(), i = size_t(uint32_t(k)) % m;
        size_t spot = m;                            // первая могилка на пути
        while (st[i] != EMPTY) {
            if (st[i] == FULL && key[i] == k) return;
            if (st[i] == DEAD && spot == m) spot = i;
            i = (i + 1) % m;
        }
        if (spot == m) spot = i;
        key[spot] = k; st[spot] = FULL; ++n;        // + rehash при α > 0.7
    }
    void erase(int k) {
        size_t m = key.size(), i = size_t(uint32_t(k)) % m;
        while (st[i] != EMPTY) {
            if (st[i] == FULL && key[i] == k) { st[i] = DEAD; --n; return; }
            i = (i + 1) % m;
        }
    }
};
```

Здесь два классических капкана, и оба ловит стресс-тест:

> [!warning] Капкан 1: erase не имеет права ставить EMPTY
> Поиск останавливается на пустой ячейке. Сотрите ячейку в середине чьего-то маршрута проб — и живой ключ дальше по маршруту станет «ненайденным». Поэтому **могилка** (DEAD): поиск идёт сквозь неё, вставка может её переиспользовать. Могилки копятся и портят эффективную α — при их избытке таблицу пересобирают.

> [!warning] Капкан 2: insert не имеет права писать в первую же могилку
> Соблазн — вставить в первую не-FULL ячейку. Но ключ k может лежать **дальше** по маршруту, за могилкой: получите дубликат (и рассинхрон size с эталоном). Честный insert сканирует до самой пустоты, проверяя k, запоминает первую могилку по пути — и пишет в неё лишь убедившись, что ключа нет.

## Секундомер: три таблицы

```
# int-ключи, загрузка α ≈ 0.5
                     вставка    поиск
цепочки (наши)         76 мс    10 мс
открытая (наша)         4 мс     8 мс
std::unordered_set     55 мс    31 мс
# чек-суммы поиска совпали у всех трёх
```

Обе наши обгоняют библиотечную — и это не магия, а знакомый мотив «цена гарантии» (занятие 2): стандарт требует от unordered стабильных адресов элементов, поэтому каждый ключ живёт в отдельном узле в куче — аллокация при вставке, прыжок при поиске. Открытая адресация быстрее цепочек на вставке в 19 раз: ни одной аллокации вообще, массив выделен заранее; у цепочек первый `push_back` в каждое ведро — это malloc.

## Полиномиальный хеш строки

$$h(s) = s_0 B^{n-1} + s_1 B^{n-2} + \dots + s_{n-1} \pmod{2^{64}}$$

```cpp
struct PolyHash {
    size_t operator()(const std::string& s) const {
        uint64_t h = 0;
        for (unsigned char c : s) h = h * 131 + c;   // mod 2^64 — сам собой
        return h;
    }
};
std::unordered_set<std::string, PolyHash> dict;
```

Это запись строки как числа в системе счисления с основанием B = 131 — «цифры» здесь байты букв (семестр 1, занятие 4: длинные числа). Наивная «сумма букв» кладёт все **анаграммы** в одно ведро («листок»/«столик»); полином помнит позиции. Переполнение uint64 — бесплатный mod $2^{64}$ (беззнаковые переполняются по модулю легально — семестр 1, занятие 3). Для соревнований mod $2^{64}$ ломается анти-хеш тестами — лечение вчерашнее: случайная база B при старте.

```
# 10^6 случайных строк длины 16
                     вставка    поиск
std::hash<string>      76 мс    37 мс
наш PolyHash(131)      97 мс    56 мс
```

Библиотечный быстрее — внутри CityHash-подобные функции, жующие строку по 8 байт за шаг, наш цикл — по байту. Зачем тогда полином? **Свойства**: контролируемая (в т.ч. случайная) база, простая математика и главный бонус — хеш любой подстроки за O(1) после препроцессинга префиксов: дверь в строковые алгоритмы, которая за рамками семестра, но совсем рядом. Правило: для словаря — std::hash, для алгоритмических трюков со строками — полином.

## Свой тип — свой хеш

```cpp
struct Point {
    int x, y;
    bool operator==(const Point&) const = default;   // == обязателен
};

template <>
struct std::hash<Point> {
    size_t operator()(const Point& p) const {
        size_t h1 = std::hash<int>{}(p.x);
        size_t h2 = std::hash<int>{}(p.y);
        return h1 ^ (h2 + 0x9e3779b97f4a7c15ull + (h1 << 6) + (h1 >> 2));
    }
};

std::unordered_map<Point, int> visits;
visits[{3, 5}]++;
```

unordered-контейнеру нужны двое — hash и `operator==`, и они обязаны дружить: **равные объекты ⇒ равные хеши** (обратное не требуется). Голый XOR полей — ловушка прошлого семинара: $(a,b)$ и $(b,a)$ слипаются, $(a,a)$ — все в ноль; hash_combine ломает симметрию сдвигами и константой золотого сечения. Специализация в `namespace std` легальна именно для своих типов (семестр 1, занятие 24).

## Стресс-тест: три таблицы под одним судьёй

```cpp
ChainSet a;  OpenSet b(1 << 20);  std::unordered_set<int> ref;
std::mt19937 rng(42);
for (int step = 0; step < 100'000; ++step) {
    int k = int(rng() % 1000);                  // тесно: коллизии и могилки — часто
    switch (rng() % 3) {
      case 0: a.insert(k); b.insert(k); ref.insert(k); break;
      case 1: assert(a.find(k) == (ref.count(k) > 0));
              assert(b.find(k) == (ref.count(k) > 0)); break;
      case 2: a.erase(k); b.erase(k); ref.erase(k); break;
    }
}
```

Методика неизменна с занятия 3. Именно этот тест ловит оба капкана открытой адресации: замените DEAD на EMPTY в erase — и find разойдётся с эталоном через сотню шагов; упростите insert до «первой не-FULL ячейки» — и появятся дубликаты. Для ChainSet стресс с маленькой стартовой таблицей дополнительно гоняет десятки рехешей.

## Задачи практикума

1. **Группы анаграмм.** 10⁵ слов; сгруппируйте анаграммы. Каким должен быть ключ группы?

   {{% expand title="Разбор" %}}Два канонических ключа: отсортированная строка (O(len·log len) на слово) и вектор из 26 счётчиков букв (O(len)). Счётчики дешевле асимптотически и не требуют сортировки; чтобы использовать их как ключ hash-таблицы, сверните счётчики полиномиальным хешем (или используйте сам вектор как ключ со своим hash). Группировка: unordered_map<ключ, vector<string>> — один проход по словам.{{% /expand %}}

2. **Первый повтор.** Поток чисел; найдите первое значение, встретившееся второй раз.

   {{% expand title="Разбор" %}}Множество увиденных: идём по потоку, `insert` возвращает факт «уже был» (или find перед insert) — первый такой ключ и есть ответ; O(n) в среднем, O(n) памяти, поток можно не хранить. Сортировка даёт O(n log n) и требует весь массив в памяти, зато без хеш-рисков и с O(1) доп. памяти при сортировке на месте — выбор зависит от того, что дороже: время, память или гарантии.{{% /expand %}}

3. **Сломай naive erase.** В OpenSet удаление по ошибке ставит EMPTY. Постройте кратчайший ломающий сценарий (таблица из 8 ячеек).

   {{% expand title="Разбор" %}}Три ключа с одним хешем h: insert(a), insert(b), insert(c) — они займут ячейки h, h+1, h+2. erase(b) «по-настоящему» очищает h+1. Теперь find(c): проба h занята чужим (a), проба h+1 ПУСТА — «ключа нет», хотя c живёт в h+2. Роли: a заставляет b и c сдвинуться; b — жертва удаления, разрывающего маршрут; c — потерянный. Минимум — три вставки, одно удаление, один поиск.{{% /expand %}}
